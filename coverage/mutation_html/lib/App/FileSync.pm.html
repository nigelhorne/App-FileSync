  230: =head1 NAME
  231: 
  232: App::FileSync - cron-driven file synchronisation without a daemon
  233: 
  234: =head1 SYNOPSIS
  235: 
  236:     filesync init --repo documents --root ~/Documents \
  237:         --transport local --server-root /srv/filesync --remote-repo documents
  238:     filesync sync --repo documents --dry-run
  239:     filesync sync --repo documents
  240: 
  241: =head1 DESCRIPTION
  242: 
  243: App::FileSync keeps one directory per client in step with a master copy on a server, and
  244: keeps a separate machine holding a replica of that master.  Every run is a short-lived CLI
  245: process suitable for cron or the Windows Task Scheduler: there is no daemon, no database
  246: and no web interface.
  247: 
  248: Only files whose content changed are transferred.  Data frames are deflated when that
  249: makes them smaller, and files of at least 64 KiB are sent as rsync-style block deltas
  250: when the other side already holds an older copy, so an edit moves the changed blocks
  251: rather than the whole file.  C<filesync sync --no-delta> forces whole files.  Each run
  252: reports the payload bytes it sent and received and how many files moved as a delta, and
  253: C<filesync log> repeats those figures for past runs.
  254: 
  255: This module holds the pieces shared by the client, the server and the admin tools:
  256: byte-transparent JSON, path validation, conflict-copy naming and atomic file writes.
  257: 
  258: =head1 FUNCTIONS
  259: 
  260: =head2 json_encode
  261: 
  262: =head2 json_decode
  263: 
  264: Encode and decode a structure as a single line of JSON.  Paths are byte strings and are
  265: not treated as UTF-8 by these functions.
  266: 
  267: =head2 validate_relpath
  268: 
  269: Returns C<(1, undef)> for a safe relative path, or C<(0, $reason)>.  Absolute paths,
  270: backslashes, control characters, empty, C<.> and C<..> components, and paths longer than
  271: 4096 bytes or with a component longer than 255 bytes are rejected.
  272: 
  273: =head2 validate_repo_name

  275: =head2 validate_client_id

  290: 
  291: =head2 write_atomic
  292: 
  293: Writes a file through a temporary file in the same directory and renames it into place.
  294: 
  295: =head1 EXAMPLES
  296: 
  297: On the server, create the master copy and allow the client once.  Then, on each
  298: client, register the directory and add a cron entry that runs every minute:
  299: 
  300:     # once, on the client
  301:     filesync init --repo documents --root /home/foo/Documents --server srv
  302: 
  303:     # crontab -e, for foo on each client
  304:     * * * * * /usr/local/bin/filesync sync --repo documents --quiet >/dev/null
  305: 
  306: The summary line is dropped so cron does not mail on every successful run;
  307: diagnostics still go to standard error, so a failure is mailed.  Every attempt,
  308: successful or not, is also appended to F<~/.filesync/logs/documents.jsonl>, and
  309: C<filesync log --repo documents --exit 1> lists the ones that failed.
  310: 
  311: Windows clients use a scheduled task rather than cron.  With the script in
  312: F<C:\filesync> and Strawberry Perl installed, the same job is set up from a
  313: command prompt:
  314: 
  315:     REM once, on the client
  316:     C:\Strawberry\perl\bin\perl.exe C:\filesync\bin\filesync init ^
  317:       --repo documents --root C:\Users\foo\Documents --server srv
  318: 
  319:     REM then create the task; it runs every minute as the current user
  320:     schtasks /Create /SC MINUTE /MO 1 /TN FileSync /F ^
  321:       /TR "C:\Strawberry\perl\bin\perl.exe C:\filesync\bin\filesync sync --repo documents --quiet"
  322: 
  323: The task runs only while that user is logged on, which suits a Documents
  324: folder; its run log is still written under F<%USERPROFILE%\.filesync\logs>, so
  325: C<filesync log --repo documents --warnings> works there too.
  326: 
  327: The master copy on the server is an ordinary directory tree, so it can be
  328: mirrored to a backup directory from the same crontab:
  329: 
  330:     # crontab -e, for foo on the server
  331:     * * * * * rsync -a --delete --exclude '.filesync-tmp-*' \
  332:         /home/foo/FileSync/ /home/foo/backups/FileSync/
  333: 
  334: Filesync writes each file to a temporary name and renames it into place, so the
  335: mirror never catches a half-written upload; the exclusion keeps the temporary
  336: files themselves out of the backup.  C<--delete> makes the copy a mirror: a
  337: deletion that reaches the master also removes the backed-up file.
  338: 
  339: To restore the master from that backup, stop the client jobs (comment out their
  340: cron lines, or disable the scheduled task) and the server's backup job, so the
  341: backup job cannot copy a half-restored tree back into the backup.  Let any
  342: running sync finish, then mirror the backup back:
  343: 
  344:     rsync -a --delete --checksum /home/foo/backups/FileSync/ /home/foo/FileSync/
  345: 
  346: C<--checksum> compares the contents, so a restored file is not skipped just
  347: because its size and modification time happen to match the newer copy.  This is
  348: a rollback rather than a merge: files created after the backup was taken
  349: disappear from the master, and the next sync propagates that to the clients, so
  350: copy anything you need to keep out of the tree first.  The server
  351: would rehash the restored files on the next session anyway, but
  352: C<filesync-admin reindex> rebuilds the index immediately, before any client
  353: reconnects; clients then pull the restored versions, merging edits they have not
  354: synced as usual.
  355: 
  356: Before re-enabling the jobs, check that the copy is exact with a read-only
  357: comparison against the backup:
  358: 
  359:     rsync -a --delete --checksum --dry-run --itemize-changes \
  360:         /home/foo/backups/FileSync/ /home/foo/FileSync/
  361: 
  362: No output and exit 0 mean the master matches the backup.  Any line beginning
  363: C<< >f >> names a path that still differs, and C<*deleting> names one the
  364: rollback should have removed.  The index still describes the pre-rollback tree,
  365: so C<filesync-admin verify> may report drift at this point; that is expected.
  366: Rebuild it and check it:
  367: 
  368:     sudo -u filesync filesync-admin reindex documents
  369:     sudo -u filesync filesync-admin verify documents --deep
  370: 
  371: C<reindex> hashes every file in the master and replaces the index atomically; it
  372: refuses to run while a sync session holds the repo lock, and it names any paths
  373: it could not index.  C<clean> and exit 0 from C<verify> confirm that the master
  374: and its index agree.  Re-enable the jobs once that check passes.
  375: 
  376: To restore just one file or directory, copy that path back instead of mirroring
  377: the whole tree, with the jobs paused as above so nothing changes the tree while
  378: the copy runs:
  379: 
  380:     rsync -a --checksum /home/foo/backups/FileSync/notes/plan.txt /home/foo/FileSync/notes/
  381:     rsync -a --checksum /home/foo/backups/FileSync/photos/ /home/foo/FileSync/photos/
  382: 
  383: The trailing slash on the second source copies the directory's contents; without
  384: it rsync would put the directory itself inside the destination.  Add C<--delete>
  385: only when that directory should match the backup exactly, since it removes files
  386: created after the backup was taken.  Everything outside the restored paths is
  387: left alone; refresh the index with C<reindex> as above, or let the next session
  388: do it, and clients pull the restored versions.  Check the restored paths with the
  389: matching C<rsync --dry-run --itemize-changes> comparison before re-enabling the
  390: jobs; no output means they match the backup.
  391: 
  392: Adjust F</usr/local/bin/filesync> to where the script was installed, because
  393: cron's default PATH rarely includes a per-user Perl bin directory.
