  229: =head1 NAME
  230: 
  231: App::FileSync - cron-driven file synchronisation without a daemon
  232: 
  233: =head1 SYNOPSIS
  234: 
  235:     filesync init --repo documents --root ~/Documents \
  236:         --transport local --server-root /srv/filesync --remote-repo documents
  237:     filesync sync --repo documents --dry-run
  238:     filesync sync --repo documents
  239: 
  240: =head1 DESCRIPTION
  241: 
  242: App::FileSync keeps one directory per client in step with a master copy on a server, and
  243: keeps a separate machine holding a replica of that master.  Every run is a short-lived CLI
  244: process suitable for cron or the Windows Task Scheduler: there is no daemon, no database
  245: and no web interface.
  246: 
  247: Only files whose content changed are transferred.  Data frames are deflated when that
  248: makes them smaller, and files of at least 64 KiB are sent as rsync-style block deltas
  249: when the other side already holds an older copy, so an edit moves the changed blocks
  250: rather than the whole file.  C<filesync sync --no-delta> forces whole files.  Each run
  251: reports the payload bytes it sent and received and how many files moved as a delta, and
  252: C<filesync log> repeats those figures for past runs.
  253: 
  254: The design and its rationale are in F<SPEC.md> in the distribution root.
  255: 
  256: This module holds the pieces shared by the client, the server and the admin tools:
  257: byte-transparent JSON, path validation, conflict-copy naming and atomic file writes.
  258: 
  259: =head1 FUNCTIONS
  260: 
  261: =head2 json_encode
  262: 
  263: =head2 json_decode
  264: 
  265: Encode and decode a structure as a single line of JSON.  Paths are byte strings and are
  266: not treated as UTF-8 by these functions.

  269:

  271: backslashes, control characters, empty, C<.> and C<..> components, and paths longer than

  293: 
  294: Writes a file through a temporary file in the same directory and renames it into place.
  295: 
  296: =head1 EXAMPLES
  297: 
  298: On the server, create the master copy and allow the client once.  Then, on each
  299: client, register the directory and add a cron entry that runs every minute:
  300: 
  301:     # once, on the client
  302:     filesync init --repo documents --root /home/foo/Documents --server srv
  303: 
  304:     # crontab -e, for foo on each client
  305:     * * * * * /usr/local/bin/filesync sync --repo documents --quiet >/dev/null
  306: 
  307: The summary line is dropped so cron does not mail on every successful run;
  308: diagnostics still go to standard error, so a failure is mailed.  Every attempt,
  309: successful or not, is also appended to F<~/.filesync/logs/documents.jsonl>, and
  310: C<filesync log --repo documents --exit 1> lists the ones that failed.
  311: 
  312: Windows clients use a scheduled task rather than cron.  With the script in
  313: F<C:\filesync> and Strawberry Perl installed, the same job is set up from a
  314: command prompt:
  315: 
  316:     REM once, on the client
  317:     C:\Strawberry\perl\bin\perl.exe C:\filesync\bin\filesync init ^
  318:       --repo documents --root C:\Users\foo\Documents --server srv
  319: 
  320:     REM then create the task; it runs every minute as the current user
  321:     schtasks /Create /SC MINUTE /MO 1 /TN FileSync /F ^
  322:       /TR "C:\Strawberry\perl\bin\perl.exe C:\filesync\bin\filesync sync --repo documents --quiet"
  323: 
  324: The task runs only while that user is logged on, which suits a Documents
  325: folder; its run log is still written under F<%USERPROFILE%\.filesync\logs>, so
  326: C<filesync log --repo documents --warnings> works there too.
  327: 
  328: The master copy on the server is an ordinary directory tree, so it can be
  329: mirrored to a backup directory from the same crontab:
  330: 
  331:     # crontab -e, for foo on the server
  332:     * * * * * rsync -a --delete --exclude '.filesync-tmp-*' \
  333:         /home/foo/FileSync/ /home/foo/backups/FileSync/
  334: 
  335: Filesync writes each file to a temporary name and renames it into place, so the
  336: mirror never catches a half-written upload; the exclusion keeps the temporary
  337: files themselves out of the backup.  C<--delete> makes the copy a mirror: a
  338: deletion that reaches the master also removes the backed-up file.
  339: 
  340: To restore the master from that backup, stop the client jobs (comment out their
  341: cron lines, or disable the scheduled task) and the server's backup job, so the
  342: backup job cannot copy a half-restored tree back into the backup.  Let any
  343: running sync finish, then mirror the backup back:
  344: 
  345:     rsync -a --delete --checksum /home/foo/backups/FileSync/ /home/foo/FileSync/
  346: 
  347: C<--checksum> compares the contents, so a restored file is not skipped just
  348: because its size and modification time happen to match the newer copy.  This is
  349: a rollback rather than a merge: files created after the backup was taken
  350: disappear from the master, and the next sync propagates that to the clients, so
  351: copy anything you need to keep out of the tree first.  The server
  352: would rehash the restored files on the next session anyway, but
  353: C<filesync-admin reindex> rebuilds the index immediately, before any client
  354: reconnects; clients then pull the restored versions, merging edits they have not
  355: synced as usual.
  356: 
  357: Before re-enabling the jobs, check that the copy is exact with a read-only
  358: comparison against the backup:
  359: 
  360:     rsync -a --delete --checksum --dry-run --itemize-changes \
  361:         /home/foo/backups/FileSync/ /home/foo/FileSync/
  362: 
  363: No output and exit 0 mean the master matches the backup.  Any line beginning
  364: C<< >f >> names a path that still differs, and C<*deleting> names one the
  365: rollback should have removed.  The index still describes the pre-rollback tree,
  366: so C<filesync-admin verify> may report drift at this point; that is expected.
  367: Rebuild it and check it:
  368: 
  369:     sudo -u filesync filesync-admin reindex documents
  370:     sudo -u filesync filesync-admin verify documents --deep
  371: 
  372: C<reindex> hashes every file in the master and replaces the index atomically; it
  373: refuses to run while a sync session holds the repo lock, and it names any paths
  374: it could not index.  C<clean> and exit 0 from C<verify> confirm that the master
  375: and its index agree.  Re-enable the jobs once that check passes.
  376: 
  377: To restore just one file or directory, copy that path back instead of mirroring
  378: the whole tree, with the jobs paused as above so nothing changes the tree while
  379: the copy runs:
  380: 
  381:     rsync -a --checksum /home/foo/backups/FileSync/notes/plan.txt /home/foo/FileSync/notes/
  382:     rsync -a --checksum /home/foo/backups/FileSync/photos/ /home/foo/FileSync/photos/
  383: 
  384: The trailing slash on the second source copies the directory's contents; without
  385: it rsync would put the directory itself inside the destination.  Add C<--delete>
  386: only when that directory should match the backup exactly, since it removes files
  387: created after the backup was taken.  Everything outside the restored paths is
  388: left alone; refresh the index with C<reindex> as above, or let the next session
  389: do it, and clients pull the restored versions.  Check the restored paths with the
  390: matching C<rsync --dry-run --itemize-changes> comparison before re-enabling the
  391: jobs; no output means they match the backup.
  392: 
  393: Adjust F</usr/local/bin/filesync> to where the script was installed, because
  394: cron's default PATH rarely includes a per-user Perl bin directory.
