   91: =head1 DESCRIPTION
   92: 
   93: App::FileSync keeps one directory per client in step with a master copy on a server, and
   94: keeps a separate machine holding a replica of that master.  Every run is a short-lived CLI
   95: process suitable for cron or the Windows Task Scheduler: there is no daemon, no database
   96: and no web interface.
   97: 
   98: Only files whose content changed are transferred.  Data frames are deflated when that
   99: makes them smaller, and files of at least 64 KiB are sent as rsync-style block deltas
  100: when the other side already holds an older copy, so an edit moves the changed blocks
  101: rather than the whole file.  C<filesync sync --no-delta> forces whole files.  Each run
  102: reports the payload bytes it sent and received and how many files moved as a delta, and
  103: C<filesync log> repeats those figures for past runs.
  104: 
  105: Every message the tools print is looked up in a catalogue
  106: (L<App::FileSync::I18N>), so a translation is one new catalogue.

  506: 		  !defined $value                          ? [ undef, 0 ]

  713: 	# flattened rather than trusted.

  715: 	$id =~ s/[^A-Za-z0-9._-]+/_/g;
  716: 	$id = $UNKNOWN_CLIENT unless length $id;

  718: 	my $tail = ".conflict-$id-" . format_utc($epoch) . $ext;

  720: 	# Keep the whole name inside the 255-byte limit of common filesystems.
  721: 	my $room = $CONFLICT_NAME_BYTES - length($tail);

  723: 	$stem = substr($stem, 0, $room) if length($stem) > $room;

  725: 	return _join_dir($dir, $stem . $tail);

  753: =head1 EXAMPLES
  754: 
  755: On the server, create the master copy and allow the client once.  Then, on each
  756: client, register the directory and add a cron entry that runs every minute:
  757: 
  758:     # once, on the client
  759:     filesync init --repo documents --root /home/foo/Documents --server srv
  760: 
  761:     # crontab -e, for foo on each client
  762:     * * * * * /usr/local/bin/filesync sync --repo documents --quiet >/dev/null
  763: 
  764: The summary line is dropped so cron does not mail on every successful run;
  765: diagnostics still go to standard error, so a failure is mailed.  Every attempt,
  766: successful or not, is also appended to F<~/.filesync/logs/documents.jsonl>, and
  767: C<filesync log --repo documents --exit 1> lists the ones that failed.
  768: 
  769: Windows clients use a scheduled task rather than cron.  With the script in
  770: F<C:\filesync> and Strawberry Perl installed, the same job is set up from a
  771: command prompt:
  772: 
  773:     REM once, on the client
  774:     C:\Strawberry\perl\bin\perl.exe C:\filesync\bin\filesync init ^
  775:       --repo documents --root C:\Users\foo\Documents --server srv
  776: 
  777:     REM then create the task; it runs every minute as the current user
  778:     schtasks /Create /SC MINUTE /MO 1 /TN FileSync /F ^
  779:       /TR "C:\Strawberry\perl\bin\perl.exe C:\filesync\bin\filesync sync --repo documents --quiet"
  780: 
  781: The task runs only while that user is logged on, which suits a Documents
  782: folder; its run log is still written under F<%USERPROFILE%\.filesync\logs>, so
  783: C<filesync log --repo documents --warnings> works there too.
  784: 
  785: The master copy on the server is an ordinary directory tree, so it can be
  786: mirrored to a backup directory from the same crontab:
  787: 
  788:     # crontab -e, for foo on the server
  789:     * * * * * rsync -a --delete --exclude '.filesync-tmp-*' \
  790:         /home/foo/FileSync/ /home/foo/backups/FileSync/
  791: 
  792: Filesync writes each file to a temporary name and renames it into place, so the
  793: mirror never catches a half-written upload; the exclusion keeps the temporary
  794: files themselves out of the backup.  C<--delete> makes the copy a mirror: a
  795: deletion that reaches the master also removes the backed-up file.
  796: 
  797: To restore the master from that backup, stop the client jobs (comment out their
  798: cron lines, or disable the scheduled task) and the server's backup job, so the
  799: backup job cannot copy a half-restored tree back into the backup.  Let any
  800: running sync finish, then mirror the backup back:
  801: 
  802:     rsync -a --delete --checksum /home/foo/backups/FileSync/ /home/foo/FileSync/
  803: 
  804: C<--checksum> compares the contents, so a restored file is not skipped just
  805: because its size and modification time happen to match the newer copy.  This is
  806: a rollback rather than a merge: files created after the backup was taken
  807: disappear from the master, and the next sync propagates that to the clients, so
  808: copy anything you need to keep out of the tree first.  The server
  809: would rehash the restored files on the next session anyway, but
  810: C<filesync-admin reindex> rebuilds the index immediately, before any client
  811: reconnects; clients then pull the restored versions, merging edits they have not
  812: synced as usual.
  813: 
  814: Before re-enabling the jobs, check that the copy is exact with a read-only
  815: comparison against the backup:
  816: 
  817:     rsync -a --delete --checksum --dry-run --itemize-changes \
  818:         /home/foo/backups/FileSync/ /home/foo/FileSync/
  819: 
  820: No output and exit 0 mean the master matches the backup.  Any line beginning
  821: C<< >f >> names a path that still differs, and C<*deleting> names one the
  822: rollback should have removed.  The index still describes the pre-rollback tree,
  823: so C<filesync-admin verify> may report drift at this point; that is expected.
  824: Rebuild it and check it:
  825: 
  826:     sudo -u filesync filesync-admin reindex documents
  827:     sudo -u filesync filesync-admin verify documents --deep
  828: 
  829: C<reindex> hashes every file in the master and replaces the index atomically; it
  830: refuses to run while a sync session holds the repo lock, and it names any paths
  831: it could not index.  C<clean> and exit 0 from C<verify> confirm that the master
  832: and its index agree.  Re-enable the jobs once that check passes.
  833: 
  834: To restore just one file or directory, copy that path back instead of mirroring
  835: the whole tree, with the jobs paused as above so nothing changes the tree while
  836: the copy runs:
  837: 
  838:     rsync -a --checksum /home/foo/backups/FileSync/notes/plan.txt /home/foo/FileSync/notes/
  839:     rsync -a --checksum /home/foo/backups/FileSync/photos/ /home/foo/FileSync/photos/
  840: 
  841: The trailing slash on the second source copies the directory's contents; without
  842: it rsync would put the directory itself inside the destination.  Add C<--delete>
  843: only when that directory should match the backup exactly, since it removes files
  844: created after the backup was taken.  Everything outside the restored paths is
  845: left alone; refresh the index with C<reindex> as above, or let the next session
  846: do it, and clients pull the restored versions.  Check the restored paths with the
  847: matching C<rsync --dry-run --itemize-changes> comparison before re-enabling the
  848: jobs; no output means they match the backup.
  849: 
  850: Adjust F</usr/local/bin/filesync> to where the script was installed, because
  851: cron's default PATH rarely includes a per-user Perl bin directory.

  853: =head1 LIMITATIONS
  854: 
  855: These are the design weaknesses a reviewer should weigh before relying on the
  856: tool.  None of them loses data silently; most cost time or space.
  857: 
  858: =over 4
  859: 
  860: =item * B<One master.>  The topology is a star around one server.  The replica
  861: is a pull-only mirror, not a failover: if the server is lost, clients stop
  862: until an administrator points them at a rebuilt master.
  863: 
  864: =item * B<Every run exchanges the whole manifest.>  The client sends one entry
  865: per file and the server answers with the whole plan as a single JSON line, so
  866: a run costs O(files) in time, memory and bandwidth even when nothing changed.
  867: A tree of a million files means a plan message of the order of a hundred
  868: megabytes.  A change journal or Merkle summary would remove that, at the cost
  869: of the "everything is inspectable with cat" property.
  870: 
  871: =item * B<No line-length cap on the wire.>  Because of the previous point, a
  872: control message cannot be bounded without breaking large trees.  The peer is
  873: authenticated by ssh and pinned by the forced command, so this is a resource
  874: risk from a misbehaving client, not from the network.
  875: 
  876: =item * B<Lock-step protocol.>  One request is in flight at a time and each
  877: 256 KiB chunk waits for its acknowledgement, so throughput is bound by the
  878: round-trip time on a high-latency link.
  879: 
  880: =item * B<Clock-dependent tie-breaks.>  When both sides changed a file, the
  881: newer mtime wins (the master wins ties within 2 seconds).  A client with a
  882: wrong clock picks the wrong winner; the loser is still kept as a conflict copy.
  883: 
  884: =item * B<No fsync.>  Renames are atomic between processes but not durable
  885: across a power cut; see L<App::FileSync::IO/LIMITATIONS>.
  886: 
  887: =item * B<Pure-Perl deltas are bounded.>  Only the first 8 MiB after the
  888: unchanged prefix are scanned for moved blocks; later changes go as literals.
  889: See L<App::FileSync::Delta>.
  890: 
  891: =item * B<What is not synced.>  Symlinks, devices, sockets, extended attributes,
  892: ACLs and ownership.  Permission bits are carried only between POSIX systems.
  893: 
  894: =item * B<Names.>  Unicode normalisation is not reconciled, so the same name
  895: in NFC (Linux) and NFD (older macOS) is two different files.  A
  896: case-insensitive client cannot hold two master paths that differ only in case.
  897: 
  898: =item * B<Encapsulation costs.>  Private methods use L<Sub::Private> in
  899: C<enforce> mode, which costs about 1.4 microseconds per call (measured on
  900: 5.40).  Helpers that run per file or per JSON value (the merge comparisons,
  901: the JSON byte downgrade, the rolling checksum) are therefore lexical code
  902: references: private by scope, with no wrapper.  Both Sub::Private and
  903: L<Sub::Protected> are bypassed while C<HARNESS_ACTIVE> is set.
  904: 
  905: =item * B<Validation costs.>  L<Params::Validate::Strict> costs about 11
  906: microseconds per call, so it guards the public entry points that run a few
  907: times per command (constructors, admin and client operations).  Functions that
  908: run per path or per protocol frame (L</validate_relpath>, the protocol
  909: methods, the scanner) check their arguments by hand.
  910: 
  911: =item * B<Errors carry locations.>  Library errors are raised with C<croak> and
  912: so end with C<at FILE line N.>; the commands strip that before printing, and
  913: C<FILESYNC_TRACE=1> turns every error into a full stack trace instead.
  914: 
  915: =item * B<English only.>  The catalogue mechanism supports other languages,
  916: plural forms and gender, but only the English catalogue ships.
