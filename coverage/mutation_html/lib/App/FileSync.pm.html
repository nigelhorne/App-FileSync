   91: =head1 DESCRIPTION
   92: 
   93: App::FileSync keeps one directory per client in step with a master copy on a server, and
   94: keeps a separate machine holding a replica of that master.  Every run is a short-lived CLI
   95: process suitable for cron or the Windows Task Scheduler: there is no daemon, no database
   96: and no web interface.
   97: 
   98: Only files whose content changed are transferred.  Data frames are deflated when that
   99: makes them smaller, and files of at least 64 KiB are sent as rsync-style block deltas
  100: when the other side already holds an older copy, so an edit moves the changed blocks
  101: rather than the whole file.  C<filesync sync --no-delta> forces whole files.  Each run
  102: reports the payload bytes it sent and received and how many files moved as a delta, and
  103: C<filesync log> repeats those figures for past runs.
  104: 
  105: Every message the tools print is looked up in a catalogue
  106: (L<App::FileSync::I18N>), so a translation is one new catalogue.

  508: 		  !defined $value                          ? [ undef, 0 ]
  509: 		: $value =~ /\A\d+\z/                      ? [ $value + 0, 0 ]

  715: 	# flattened rather than trusted.

  717: 	$id =~ s/[^A-Za-z0-9._-]+/_/g;
  718: 	$id = $UNKNOWN_CLIENT unless length $id;
  719: 
  720: 	my $tail = ".conflict-$id-" . format_utc($epoch) . $ext;
  721: 
  722: 	# Keep the whole name inside the 255-byte limit of common filesystems.
  723: 	my $room = $CONFLICT_NAME_BYTES - length($tail);

  727: 	return _join_dir($dir, $stem . $tail);

  759: =head1 EXAMPLES
  760: 
  761: On the server, create the master copy and allow the client once.  Then, on each
  762: client, register the directory and add a cron entry that runs every minute:
  763: 
  764: 	# once, on the client
  765: 	filesync init --repo documents --root /home/foo/Documents --server srv
  766: 
  767: 	# crontab -e, for foo on each client
  768: 	* * * * * /usr/local/bin/filesync sync --repo documents --quiet >/dev/null
  769: 
  770: The summary line is dropped so cron does not mail on every successful run;
  771: diagnostics still go to standard error, so a failure is mailed.  Every attempt,
  772: successful or not, is also appended to F<~/.filesync/logs/documents.jsonl>, and
  773: C<filesync log --repo documents --exit 1> lists the ones that failed.
  774: 
  775: Windows clients use a scheduled task rather than cron.  With the script in
  776: F<C:\filesync> and Strawberry Perl installed, the same job is set up from a
  777: command prompt:
  778: 
  779: 	REM once, on the client
  780: 	C:\Strawberry\perl\bin\perl.exe C:\filesync\bin\filesync init ^
  781: 	  --repo documents --root C:\Users\foo\Documents --server srv
  782: 
  783: 	REM then create the task; it runs every minute as the current user
  784: 	schtasks /Create /SC MINUTE /MO 1 /TN FileSync /F ^
  785: 	  /TR "C:\Strawberry\perl\bin\perl.exe C:\filesync\bin\filesync sync --repo documents --quiet"
  786: 
  787: The task runs only while that user is logged on, which suits a Documents
  788: folder; its run log is still written under F<%USERPROFILE%\.filesync\logs>, so
  789: C<filesync log --repo documents --warnings> works there too.
  790: 
  791: The master copy on the server is an ordinary directory tree, so it can be
  792: mirrored to a backup directory from the same crontab:
  793: 
  794: 	# crontab -e, for foo on the server
  795: 	* * * * * rsync -a --delete --exclude '.filesync-tmp-*' \
  796: 	    /home/foo/FileSync/ /home/foo/backups/FileSync/
  797: 
  798: Filesync writes each file to a temporary name and renames it into place, so the
  799: mirror never catches a half-written upload; the exclusion keeps the temporary
  800: files themselves out of the backup.  C<--delete> makes the copy a mirror: a
  801: deletion that reaches the master also removes the backed-up file.
  802: 
  803: To restore the master from that backup, stop the client jobs (comment out their
  804: cron lines, or disable the scheduled task) and the server's backup job, so the
  805: backup job cannot copy a half-restored tree back into the backup.  Let any
  806: running sync finish, then mirror the backup back:
  807: 
  808: 	rsync -a --delete --checksum /home/foo/backups/FileSync/ /home/foo/FileSync/
  809: 
  810: C<--checksum> compares the contents, so a restored file is not skipped just
  811: because its size and modification time happen to match the newer copy.  This is
  812: a rollback rather than a merge: files created after the backup was taken
  813: disappear from the master, and the next sync propagates that to the clients, so
  814: copy anything you need to keep out of the tree first.  The server
  815: would rehash the restored files on the next session anyway, but
  816: C<filesync-admin reindex> rebuilds the index immediately, before any client
  817: reconnects; clients then pull the restored versions, merging edits they have not
  818: synced as usual.
  819: 
  820: Before re-enabling the jobs, check that the copy is exact with a read-only
  821: comparison against the backup:
  822: 
  823: 	rsync -a --delete --checksum --dry-run --itemize-changes \
  824: 	    /home/foo/backups/FileSync/ /home/foo/FileSync/
  825: 
  826: No output and exit 0 mean the master matches the backup.  Any line beginning
  827: C<< >f >> names a path that still differs, and C<*deleting> names one the
  828: rollback should have removed.  The index still describes the pre-rollback tree,
  829: so C<filesync-admin verify> may report drift at this point; that is expected.
  830: Rebuild it and check it:
  831: 
  832: 	sudo -u filesync filesync-admin reindex documents
  833: 	sudo -u filesync filesync-admin verify documents --deep
  834: 
  835: C<reindex> hashes every file in the master and replaces the index atomically; it
  836: refuses to run while a sync session holds the repo lock, and it names any paths
  837: it could not index.  C<clean> and exit 0 from C<verify> confirm that the master
  838: and its index agree.  Re-enable the jobs once that check passes.
  839: 
  840: To restore just one file or directory, copy that path back instead of mirroring
  841: the whole tree, with the jobs paused as above so nothing changes the tree while
  842: the copy runs:
  843: 
  844: 	rsync -a --checksum /home/foo/backups/FileSync/notes/plan.txt /home/foo/FileSync/notes/
  845: 	rsync -a --checksum /home/foo/backups/FileSync/photos/ /home/foo/FileSync/photos/
  846: 
  847: The trailing slash on the second source copies the directory's contents; without
  848: it rsync would put the directory itself inside the destination.  Add C<--delete>
  849: only when that directory should match the backup exactly, since it removes files
  850: created after the backup was taken.  Everything outside the restored paths is
  851: left alone; refresh the index with C<reindex> as above, or let the next session
  852: do it, and clients pull the restored versions.  Check the restored paths with the
  853: matching C<rsync --dry-run --itemize-changes> comparison before re-enabling the
  854: jobs; no output means they match the backup.
  855: 
  856: Adjust F</usr/local/bin/filesync> to where the script was installed, because
  857: cron's default PATH rarely includes a per-user Perl bin directory.

  859: =head1 LIMITATIONS
  860: 
  861: These are the design weaknesses a reviewer should weigh before relying on the
  862: tool.  None of them loses data silently; most cost time or space.
  863: 
  864: =over 4
  865: 
  866: =item * B<One master.>  The topology is a star around one server.  The replica
  867: is a pull-only mirror, not a failover: if the server is lost, clients stop
  868: until an administrator points them at a rebuilt master.
  869: 
  870: =item * B<Every run exchanges the whole manifest.>  The client sends one entry
  871: per file and the server answers with the whole plan as a single JSON line, so
  872: a run costs O(files) in time, memory and bandwidth even when nothing changed.
  873: A tree of a million files means a plan message of the order of a hundred
  874: megabytes.  A change journal or Merkle summary would remove that, at the cost
  875: of the "everything is inspectable with cat" property.
  876: 
  877: =item * B<No line-length cap on the wire.>  Because of the previous point, a
  878: control message cannot be bounded without breaking large trees.  The peer is
  879: authenticated by ssh and pinned by the forced command, so this is a resource
  880: risk from a misbehaving client, not from the network.
  881: 
  882: =item * B<Lock-step protocol.>  One request is in flight at a time and each
  883: 256 KiB chunk waits for its acknowledgement, so throughput is bound by the
  884: round-trip time on a high-latency link.
  885: 
  886: =item * B<Clock-dependent tie-breaks.>  When both sides changed a file, the
  887: newer mtime wins (the master wins ties within 2 seconds).  A client with a
  888: wrong clock picks the wrong winner; the loser is still kept as a conflict copy.
  889: 
  890: =item * B<No fsync.>  Renames are atomic between processes but not durable
  891: across a power cut; see L<App::FileSync::IO/LIMITATIONS>.
  892: 
  893: =item * B<Pure-Perl deltas are bounded.>  Only the first 8 MiB after the
  894: unchanged prefix are scanned for moved blocks; later changes go as literals.
  895: See L<App::FileSync::Delta>.
  896: 
  897: =item * B<What is not synced.>  Symlinks, devices, sockets, extended attributes,
  898: ACLs and ownership.  Permission bits are carried only between POSIX systems.
  899: 
  900: =item * B<Names.>  Unicode normalisation is not reconciled, so the same name
  901: in NFC (Linux) and NFD (older macOS) is two different files.  A
  902: case-insensitive client cannot hold two master paths that differ only in case.
  903: 
  904: =item * B<Encapsulation costs.>  Private methods use L<Sub::Private> in
  905: C<enforce> mode, which costs about 1.4 microseconds per call (measured on
  906: 5.40).  Helpers that run per file or per JSON value (the merge comparisons,
  907: the JSON byte downgrade, the rolling checksum) are therefore lexical code
  908: references: private by scope, with no wrapper.  Both Sub::Private and
  909: L<Sub::Protected> are bypassed while C<HARNESS_ACTIVE> is set.
  910: 
  911: =item * B<Validation costs.>  L<Params::Validate::Strict> costs about 11
  912: microseconds per call, so it guards the public entry points that run a few
  913: times per command (constructors, admin and client operations).  Functions that
  914: run per path or per protocol frame (L</validate_relpath>, the protocol
  915: methods, the scanner) check their arguments by hand.
  916: 
  917: =item * B<Errors carry locations.>  Library errors are raised with C<croak> and
  918: so end with C<at FILE line N.>; the commands strip that before printing, and
  919: C<FILESYNC_TRACE=1> turns every error into a full stack trace instead.
  920: 
  921: =item * B<English only.>  The catalogue mechanism supports other languages,
  922: plural forms and gender, but only the English catalogue ships.
